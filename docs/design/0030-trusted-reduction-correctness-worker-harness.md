# Design 0030: Trusted reduction correctness worker harness

- Status: Implemented runtime slice
- Date: 2026-08-12
- Extends: Designs 0018, 0021, 0028, and 0029
- Scope: role-bound materialization, fixed container execution, and structured worker output

## Context

Design 0029 deliberately stopped at controller dispatch. Its assignments could reach only workers
that advertised two new correctness execution kinds, but no worker implementation could safely
materialize or run their bundles. Reusing either accelerator fixture was invalid: fixture bundles
have different identities, fixed smoke-test sources, and `PASS` marker output rather than the
structured observations required by the differential oracle.

## Decisions

### 1. One policy type owns both role-separated contracts

`ReductionCorrectnessPolicy` is constructed from worker-local immutable facts. CUDA construction
binds a pinned image, one selected GPU, local environment identity, sandbox root, and resource
ceilings. Ascend construction additionally binds the complete selected device identity, exact
device-node inventory, fixed driver mount, and CANN environment identity.

The policy accepts only its role-specific executor and feature, the single fixed argv token,
sandbox-relative working directory, empty environment, disabled network, one device, bounded
resources, and the locally pinned image identity. A controller cannot select commands, mounts,
devices, environment, image, or broader limits.

### 2. Execution bundles are reread and materialized create-only

Before container creation, the worker rereads the assigned Artifact, verifies exact declared size
and digest, deserializes the validated domain bundle, and checks role plus task/candidate lineage.
It writes only the bundle's role-rooted files, the exact bundle document, a worker-authored
environment digest, and the checked-in trusted runner into an attempt-specific sandbox. Existing
bytes must be identical; symlinks, special files, path escape, and extra tree entries fail closed.

### 3. Docker plans remain shell-free and locally derived

Both roles derive `docker create` argv arrays with a read-only root, no network, dropped
capabilities, no-new-privileges, bounded CPU/memory/PIDs/output, read-only bundle mount, and bounded
tmpfs work area. CUDA adds exactly one selected NVIDIA device. Ascend adds the exact device nodes,
fixed read-only driver mount, and worker-derived visibility and runtime paths. The only entry point
is `python3` running the trusted materialized runner.

### 4. The trusted runner authors one structured receipt

The runner generates a C++ harness from the frozen corpus, invokes only the stable
`alloyport_reduce_sum_f32` ABI, records exact fp32 output bits and status behavior, builds through
fixed CMake targets, and writes one serialized `ReductionRunReceipt` to stdout. Build diagnostics
go to stderr. Before publication it rechecks schema, experiment, role, candidate, implementation,
corpus, environment, invocation/synchronization flags, observation order, and per-case input
identity.

The worker supervisor accepts exit zero only when stdout deserializes as a validated run receipt.
The existing fixture marker is not valid correctness evidence. The generic CUDA and Ascend
runtimes then retain their established CAS publication, generic receipt, durable journal,
device-guard, restart, and cleanup ordering. Backend registration and worker admission publish only
the runtime's exact correctness kind and role feature.

## Rejected alternatives

- Reuse fixture `PASS` markers: they contain no corpus observations or experiment identity.
- Accept a generic container assignment: it would grant the controller command and mount authority.
- Let the candidate emit the final JSON directly: the implementation under test is not receipt
  authority.
- Compare CUDA and Ascend results on a worker: comparison, calibration, and verdict authority remain
  controller-owned.
- Materialize into a shared mutable source tree: replay and cross-role isolation would be lost.

## Verification

Automated tests prove exact role and network denial, digest-verified create-only materialization,
fixed CUDA and Ascend Docker arguments, and structured-receipt terminal classification. A fake
Docker engine exercises create/start/wait/log collection and proves that valid JSON succeeds while
a legacy fixture marker becomes an integrity violation. A local smoke compiles and runs the C++
harness generated by the trusted Python runner against a minimal implementation.

This slice exposes reusable correctness supervisors and runtimes but does not yet add standalone
worker-file variants or claim real CUDA/Ascend evidence. The next slice must connect strict
production configuration to these constructors, then run the frozen corpus on both pinned-device
workers and archive the resulting run, calibration, and Correctness receipts.
